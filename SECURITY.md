# Security Notes — Telegram Bot Starter Kit

## Threat model

A webhook bot exposes one public HTTPS endpoint. The risks that matter:

1. **Forged updates** — anyone who discovers the webhook URL can POST fake
   Telegram updates and puppet your bot.
2. **Token leakage** — the bot token is full control of the bot (send messages
   as it, read its updates, change its webhook).
3. **Container compromise** — a bug in a dependency shouldn't yield root.

## Mitigations built into this template

### 1. Secret-token validation on every update
`setWebhook` is called with `secret_token=WEBHOOK_SECRET` (generated by Railway
as `${{ secret(32) }}`, never committed anywhere). Telegram then sends that
value in the `X-Telegram-Bot-Api-Secret-Token` header of **every** webhook
request ([Bot API docs](https://core.telegram.org/bots/api#setwebhook)).
aiogram's `SimpleRequestHandler` compares it before an update is parsed;
requests with a missing or wrong header get **401 Unauthorized** and never
reach handler code. This is verified behavior (tested: no header → 401, wrong
header → 401, correct header → 200).

Constraints: the secret must be 1–256 chars of `A-Z a-z 0-9 _ -` — Railway's
`secret(32)` output satisfies this.

### 2. Bot token handling
- `TELEGRAM_BOT_TOKEN` is a **user-supplied Railway variable** — it is never
  hardcoded, never logged, and not baked into the image.
- The token does not appear in the webhook URL path (some tutorials do this;
  it leaks into proxy/access logs). The path is static; auth lives in the header.
- If the token leaks: revoke it via @BotFather → `/token` (issues a new one),
  update the Railway variable, redeploy.

### 3. Container hardening
- `python:3.12-slim` base, no build tools in the final image.
- Runs as unprivileged user `botuser` (uid 10001), not root.
- `PIP_NO_CACHE_DIR=1` / `--no-cache-dir` — no package cache in layers.
- All direct dependencies pinned in `requirements.txt` (aiogram 3.30.0,
  aiohttp 3.14.2, asyncpg 0.31.0 — current as of 2026-07-23). Rebuilds are
  reproducible at the direct-dependency level; run `pip freeze` after a build
  if you want transitive pins too.

### 4. Database isolation
The optional Postgres service has **no public domain** — it is reachable only
over Railway's IPv6 private network. Credentials are generated per-project via
`${{ secret(32) }}` and flow to the bot through a Railway variable reference,
never through code or git. All queries in `db.py` use parameterized statements
(`$1, $2`) — no string interpolation into SQL.

### 5. No polling
Webhook mode has a smaller attack surface than polling in one respect: the bot
makes no long-lived outbound connection loop, and all inbound traffic must
pass Railway's TLS termination plus the secret-header check.

## Your responsibilities when extending

- Treat all update content (`message.text`, callback data, usernames) as
  untrusted input. The starter HTML-escapes user text via `aiogram.html.quote`
  before echoing — keep doing that.
- Keep parameterizing SQL. Never f-string user input into queries.
- If you add admin commands, gate them on `message.from_user.id` against an
  allow-list stored in a variable, not in code.
- Bump pinned dependencies deliberately; watch aiogram release notes for
  Bot API security-relevant changes.

## Reporting

This is a starter template. If you find a vulnerability in the template code,
open a GitHub issue (or a private security advisory) on the repository.
